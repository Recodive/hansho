# Hansho SDKs

Official clients for the Hansho hub's sender API, so your backend can pair
users, define channels, templates and sounds, send notifications, pages, Live
Activities and widget feeds, and verify the hub's webhooks in a few lines.

All are small HTTP clients. Go, Node, Python, Ruby, PHP and .NET have no runtime
dependencies beyond their standard library (PHP: ext-curl and ext-json). Java
uses Jackson for JSON; Rust uses ureq (rustls), serde, serde_json, hmac and sha2.
Licence: MIT. The hub itself is AGPL-3.0.

> Go is published (`go get github.com/recodive/hansho/sdk/go`). The others are
> not on npm, PyPI, RubyGems, Packagist, Maven Central, NuGet or crates.io yet;
> until they are, build them from their directory here.

## The flow

1. **Create an API key** on the hub (`hub apikey create backend`) and keep it on
   your server. Never ship it to a client app.
2. **Define** a channel (and optionally a template and sound).
3. **Pair a user:** `CreatePairingTicket(userID)` returns a `qr` string. Render
   it as a QR code; the user scans it in the Hansho app. The ticket is single
   use and valid for 10 minutes. You get a `pairing.created` webhook.
4. **Send** a message, a page (`level: "page"`, repeats until acknowledged), a
   Live Activity or a widget feed.
5. **Listen** for webhooks (`message.delivered`, `message.acked`, `action`, ...)
   and verify every one against the raw request body.

## Behaviour shared by every SDK

- **Auth:** `Authorization: Bearer <api key>`; the base URL is the hub's public URL.
- **Levels:** `passive`, `active`, `time-sensitive`, `critical`, `page`.
- **Errors:** an answer that is not 2xx becomes a typed error with `status`,
  `code` (the hub's `{"error": ...}`), `field` for validation failures and the
  parsed `Retry-After` for 429. A failure without an answer (connection,
  timeout, cancellation) is a different error type.
- **Retries:** only idempotent calls (`GET`, `PUT`, `DELETE`) are retried, only
  on 429 and 503, at most 3 times, honouring `Retry-After` (up to 60 s) or else
  exponential backoff with jitter. `POST /messages` is never retried
  automatically, because a repeat would notify the user twice, unless you pass
  an `idempotencyKey`. The hub does not deduplicate on that key yet, so a retried
  send is at-least-once; the SDK sends it as an `Idempotency-Key` header for when
  it does. `PATCH` (activity updates) is not retried.
- **Forward compatible:** fields the SDK does not know are ignored; an unknown
  webhook event arrives as `unknown`, never as an exception.
- **No secrets in logs or errors:** API keys, ticket values and message bodies
  are never put into error messages.
- **Paths:** ids and external user ids are path-escaped, so `/`, `?`, spaces and
  unicode are safe.

## Layout

```
sdk/
  go/        Go client            (go test ./...)
  node/      Node/TS client       (npm test)
  python/    Python client        (python -m unittest)
  ruby/      Ruby client          (bundle exec rake test)
  php/       PHP client           (vendor/bin/phpunit --testsuite unit)
  java/      Java/Kotlin client   (mvn verify)
  dotnet/    .NET client          (dotnet test)
  rust/      Rust client          (cargo test)
  spec/      api.json             wire contract every test suite loads
             webhook-vectors.json signed by the hub's own dispatcher
  scripts/   run-integration.sh   every SDK against the real hub binary
             fakedevice/          a minimal stand-in for the app (pair, ack)
             stubrelay/           a minimal stand-in for Hansho's relay
  examples/  one per SDK          "pair a user and send a page"
```

`spec/webhook-vectors.json` is generated by the hub, so the SDKs verify what the
hub actually signs:

    HANSHO_GEN_VECTORS=1 go test ./internal/webhook -run SDKVectors   # in hub/

(Without the variable that test fails if the committed file is stale.)

## Testing

    (cd go && go test ./...)
    (cd node && npm ci && npm test)
    (cd python && python3 -m unittest)
    (cd ruby && bundle install && bundle exec rake test)
    (cd php && composer install && vendor/bin/phpunit --testsuite unit)
    (cd java && mvn verify)
    (cd dotnet && dotnet test)
    (cd rust && cargo test)
    ./scripts/run-integration.sh      # builds hub + stub relay, runs every SDK end to end (needs all eight toolchains)

The integration script is entirely local (127.0.0.1): a stub relay stands in for
the relay, a fake device pairs and acknowledges pages, and a local receiver
checks the signed webhooks with each SDK's own verifier.
